# 2. Overview

## Purpose

Before beginning design and development work in WEBD 3100, you need a working environment that supports the complete course workflow.

In this workshop, you will configure and verify the primary tools and services used throughout the semester:

**Figma → Git/GitHub → GitHub Pages**

These tools support three connected parts of your work:

**Figma** — Design and prototype the interface
**Git/GitHub** — Develop, version, and manage the implementation
**GitHub Pages** — Deploy and verify the working website

The objective is not simply to confirm that software is installed.

By the end of the workshop, you should be able to move through the basic WEBD 3100 workflow:

**Design → Develop → Version → Deploy → Verify**

---

## Why This Matters

During the semester, your Website Redesign Project will move progressively from design into production.

You will create designs in Figma, translate those designs into HTML and CSS, manage your implementation through Git and GitHub, and publish the resulting website through GitHub Pages.

Problems with accounts, repositories, Git configuration, file sharing, or deployment can interrupt that learning process.

Workshop 0 establishes a **known working environment** before project work begins.

It also gives the instructor an opportunity to understand the different levels of experience students bring to the course.

---

## Learning Objectives

By the end of this workshop, you should be able to:

* access and work within Figma;
* create and share a Figma design file;
* access your GitHub account;
* create or access a GitHub repository;
* clone a repository to your development computer;
* make and save a local change;
* use the basic Git workflow to commit and push a change;
* configure GitHub Pages;
* publish a basic website;
* verify that a deployment is working;
* update the website and verify that the deployed version changes; and
* explain how Figma, Git/GitHub, and GitHub Pages support the WEBD 3100 design-to-production workflow.

# 5. Concepts & Theory

Before beginning the technical tasks, it is important to understand **why these tools are being used together**.

## Figma — Design

Figma represents the design side of the workflow.

Throughout WEBD 3100, you will use it for activities including:

* visual exploration;
* style guides;
* design systems;
* wireframes;
* responsive interface designs;
* reusable components;
* interactive prototypes; and
* design critique.

Your Figma file becomes evidence of:

**What did you intend to design?**

---

## Git & GitHub — Version and Manage

Once a design begins moving into implementation, the website needs to be managed as a software project.

Git provides version control.

GitHub provides a remote location for the repository and development history.

Throughout the course, you will regularly use the workflow:

**Edit → Save → Stage → Commit → Push**

Your GitHub repository becomes evidence of:

**How did you implement and develop the website?**

---

## GitHub Pages — Deploy

A website needs to be experienced in a browser.

GitHub Pages allows a compatible repository to be published as a website.

The deployed website can then be:

* viewed;
* shared;
* tested;
* evaluated for responsiveness;
* evaluated for accessibility;
* evaluated for usability; and
* compared with the original Figma design.

GitHub Pages becomes evidence of:

**What does the user actually experience?**

# 8. Workshop Tasks

## Task 1 — Verify Figma Access

### What

Access Figma and verify that you can create and share a design file.

### Why

Figma will be the primary interface design and prototyping environment used throughout WEBD 3100.

### How

1. Sign in to Figma.
2. Confirm that you can access the Figma workspace.
3. Create a new design file.
4. Name the file:

**WEBD3100 — Workshop 0 — Your Name**

5. Create a desktop-sized frame.
6. Add:

   * a heading;
   * a short paragraph;
   * a button or simple call-to-action.
7. Rename the frame appropriately.
8. Locate the sharing controls.
9. Verify that you understand how to share the file with the instructor.

### Checkpoint

You should now have:

* a Figma file;
* a named frame;
* simple interface content; and
* working file-sharing access.

---

# 9. Task 2 — Verify GitHub Access

## What

Verify that your GitHub account is accessible and ready for course work.

## Why

GitHub will be used throughout the semester to manage implementation work and development history.

## How

1. Sign in to GitHub.
2. Verify access to your account.
3. Review your profile information.
4. Confirm that you can create or access repositories.
5. Verify that Git is available on your development computer.

From a terminal, run:

```text
git --version
```

Verify your Git configuration:

```text
git config --global user.name
git config --global user.email
```

If the values are missing or incorrect, configure them using the instructor's guidance.

### Checkpoint

You should now have:

* working GitHub access;
* Git installed;
* your Git identity configured; and
* the ability to work with repositories.

---

# 10. Task 3 — Create the Workshop Repository

## What

Create a GitHub repository that will be used to verify the development workflow.

## Why

A repository provides version control and a remote record of project development.

## How

Create a repository using the naming convention provided by your instructor.

Clone the repository to your development computer.

Open the cloned repository in your development environment.

Create:

```text
index.html
```

Add a basic HTML document containing:

* a page title;
* a main heading;
* a short paragraph;
* a link; and
* your name.

Save the file.

Preview the page locally in your browser.

### Checkpoint

You should now have:

**GitHub Repository → Local Repository → index.html → Working Local Webpage**

---

# 11. Task 4 — Commit and Push

## What

Record your first project change using Git and push it to GitHub.

## Why

Git only becomes useful when changes are recorded intentionally and consistently.

## How

Check the repository:

```text
git status
```

Stage your changes:

```text
git add .
```

Commit the changes:

```text
git commit -m "Complete Workshop 0 initial webpage"
```

Push the commit:

```text
git push
```

Open the repository on GitHub.

Verify that:

* `index.html` appears;
* your commit appears; and
* the latest code is visible.

### Checkpoint

You should be able to demonstrate:

**Local Change → Commit → Push → GitHub**

---

# 12. Task 5 — Deploy with GitHub Pages

## What

Publish the repository as a working website using GitHub Pages.

## Why

Deployment allows your implementation to be experienced and evaluated as an actual website.

## How

Using the repository settings:

1. Locate the GitHub Pages configuration.
2. Configure the appropriate deployment source.
3. Save the configuration.
4. Allow the deployment to complete.
5. Open the published website.

Verify that the page displayed through GitHub Pages matches your local `index.html`.

### Checkpoint

You should now have:

**Local Website → GitHub Repository → Published GitHub Pages Website**

---

# 13. Task 6 — Complete the Update Cycle

Publishing once is not enough.

You need to verify that you understand the complete update workflow.

## What

Modify the website and publish the updated version.

## How

Return to `index.html`.

Add:

```text
WEBD 3100 — Design → Develop → Version → Deploy → Verify
```

Save the file.

Then complete the workflow again:

```text
git status
git add .
git commit -m "Verify GitHub Pages update workflow"
git push
```

After GitHub Pages updates, reload the published website.

Confirm that the new content appears.

### Checkpoint

You have now completed the full workflow:

**Edit → Save → Commit → Push → Deploy → Verify**

# 15. Collaborative Investigation & Troubleshooting

Workshop 0 is designed to encourage collaboration.

If something does not work immediately, do not simply wait for the instructor to solve it.

Use a troubleshooting process:

**Observe → Describe → Investigate → Test → Verify**

Ask:

**What did I expect to happen?**

**What actually happened?**

**What information is the tool giving me?**

**Has someone else encountered the same problem?**

**What can I test without making the problem worse?**

Students who already have experience with a tool are encouraged to help classmates understand the workflow.

Helping someone does **not** mean completing the task for them.

Explain the process and allow the other student to perform the steps.
